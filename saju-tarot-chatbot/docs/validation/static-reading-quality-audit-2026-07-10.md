# 실제 LLM 생성물 없이 가능한 리딩 품질 정적 검수

작성일: 2026-07-10  
대상 저장소: `miziixx/myapps`  
대상 경로: `saju-tarot-chatbot`  
검수 목적: `ANTHROPIC_API_KEY` 또는 실제 Haiku/Sonnet 생성물을 볼 수 없는 상황에서, 리딩 품질을 어디까지 검증할 수 있는지 정리하고 Claude Code가 다음 검수/수정 작업에 바로 사용할 기준을 남긴다.

## 결론

실제 LLM 생성문을 보지 못하는 상황에서도 다음 품질은 정적 검수 가능하다.

- 계산 근거가 프롬프트에 들어가는지
- 기본 리딩이 AI 없이도 충분한 블록을 구성하는지
- JudgmentPack Evidence Gate가 새 결론 생성을 막는지
- 고급 리딩이 원자료를 받되 기본 판단과 모순되지 않게 앵커링되는지
- 위험한 표현, 단정, 의료/투자/결혼/퇴사 지시를 막는 안전장치가 있는지
- 타로 마이너 56장, 코트 16장, 조합 KB 51종이 설명 근거로 연결되는지
- 자미두수/사주 교차검증이 확신 조절용으로만 쓰이도록 제한되는지

단, 아래 품질은 실제 생성문 없이는 검증 완료로 보면 안 된다.

- 문장이 사용자의 체감상 “내 얘기 같다”고 느껴지는지
- 말투가 자연스럽고 과하게 기계적이지 않은지
- 고급 리딩이 정말 돈 낼 만한 밀도로 읽히는지
- 토픽 심화/후속 질문이 실제로 중복 없이 답하는지
- 안전 지시가 실제 모델 출력에서 끝까지 지켜지는지

따라서 현재 상태의 판정은 **정적 품질: 대체로 통과 / 실생성 품질: 미검증**이다.

| 안전장치 | 통과 | 시스템 프롬프트와 `judgmentEngine.ts`에 단정/퇴사/투자/결혼/건강 진단 금지가 있음 | 장문 출력 후반부에서 모델이 안전 지시를 잊는지는 생성문 필요 |

| 구체성 지시 | 통과 | 돈/건강/관계/일 조언을 구체 대상+행동으로 쓰라는 지시가 있음 | 모델이 예시 문장을 복붙하듯 반복하는지 생성문 필요 |
| 타로 마이너 심화 | 통과 | `MINOR_DEPTH`가 22~77 전체에 `scene/shadow/advice` 제공 | 실제 타로 리딩에서 카드별 장면을 모두 자연스럽게 엮는지는 생성문 필요 |
| 타로 조합 KB | 통과 | `detectCardCombos()`가 뽑힌 카드 안의 실존 조합만 감지하고 참고용으로 제공 | 질문/자리/역방향에 맞게 조합을 과장 없이 조절하는지는 생성문 필요 |
| 자미두수 교차검증 | 통과 | `formatCrossValidation()`이 확신 조절용으로만 쓰라고 제한 | 실제 문장에서 자미 용어가 새는지 생성문 필요 |
| 토픽 심화 | 부분 통과 | `buildTopicDeepInstruction()`이 domain 한정, 5섹션, 새 판단 금지를 지시 | domain 매핑이 사용자 기대와 맞는지, 1000~2500자가 충분한지는 생성문 필요 |
| 후속 질문 | 미검증 | worklog상 파이프라인/브라우저 검증 완료 기록은 있으나 이번 정적 검수에서 후속 API 응답 본문은 확인 불가 | 실제 대화 품질 검수 필요 |

## 확인된 강점

### 1. 기본 리딩은 AI 실패 시에도 상품 골격이 무너지지 않는다

`buildBasicReading()`은 이미 계산된 엔진들을 재배치한다.

- `buildInstantSummary`
- `buildPsychLayer`
- `buildEventForecast`
- `describeMonthFlow`
- `buildLifestyleGuide`

따라서 실제 LLM 호출이 없어도 최소한의 “원국 스냅샷 → 사용 설명서 → 분야 신호 → 올해 흐름 → 생활 처방” 구조는 유지된다. 이 구조는 “기본은 즉시 보여야 한다”는 제품 방향에 맞다.

### 2. 기본 리딩의 환각 방지 구조가 명확하다

기본 리딩은 `usesCompactEvidence()` 조건에서 `JudgmentPack`만 전달한다. 시스템 프롬프트도 다음을 명시한다.

- judgments에 없는 새 결론 금지
- `plainConclusion`, `evidence`, `confidence`, `allowedTone`, `forbiddenClaims` 안에서만 쓰기
- evidence id로 되돌아갈 수 있는 결론만 쓰기
- 긴 계산 원문을 펼치지 않기

이 구조는 실제 생성문 없이도 “AI가 판단자가 아니라 번역자”가 되도록 설계되어 있음을 확인할 수 있다.

### 3. 고급 리딩은 원자료를 받지만 판단 방향은 앵커로 고정된다

고급 리딩에서는 `상세 계산 근거 — 사주 원국`, `상세 계산 근거 — 대운/세운/월운/일진`, `분야별 사건 신호`가 들어간다. 동시에 `buildAnchorJudgmentPack()`이 `advanced`에서만 앵커를 붙인다.

정적 기준으로는 좋은 설계다. 기본과 고급의 결론 방향이 서로 뒤집히는 문제를 줄이면서, 고급에서는 “왜 / 얼마나 / 언제”를 더 자세히 쓸 수 있다.

### 4. 안전장치가 여러 층에 있다

안전장치는 한 곳에만 있지 않다.

- 시스템 프롬프트의 전역 안전 규칙
- `judgmentEngine.ts`의 `GLOBAL_FORBIDDEN`
- domain별 forbidden claim
- `allowedTone()`의 cautious/uncertain 말투
- `formatLuckCycles()`의 상문/조객/삼재 공포 금지 gloss
- `TAROT_FOCUSED_INSTRUCTION`의 고위험 판단 단정 금지

즉, 실제 생성문 없이도 “위험 표현을 막으려는 레일”은 확인된다.

### 5. 타로 근거 밀도가 크게 올라갔다

타로 쪽은 카드별 의미만 있는 상태보다 훨씬 나아졌다.

- 마이너 56장 각각에 현실 장면, 그늘, 조언이 있음
- 코트 카드는 인물상/성숙단계/관계 모습이 붙음
- 카드 조합 KB 51종이 가까운 흐름을 보강함
- 정/역 비율, 메이저 비율, 반복 슈트, 시작→마지막 흐름 축이 진단으로 들어감

실제 리딩을 못 봐도, “타로가 뭉뚱그린 카드 풀이로 끝날 위험”은 구조적으로 줄어든 상태다.

## 확인된 한계와 리스크

### R1. 정적 검수는 “문장 맛”을 판단하지 못한다

프롬프트가 아무리 좋아도 실제 모델이 다음을 어떻게 처리하는지는 별개다.

- 너무 장황하게 쓰는지
- 같은 조언을 반복하는지
- 예시 문장을 여러 사용자에게 비슷하게 쓰는지
- 섹션 구조를 끝까지 지키는지
- 긴 출력 후반부에서 안전 규칙을 잊는지

이건 API 키 있는 환경에서 실제 생성문을 봐야만 확인 가능하다.

### R2. 시스템 프롬프트가 매우 길고 지시가 많다

`systemPrompt.ts`의 지시는 촘촘하지만, 너무 많은 규칙이 한 프롬프트에 들어가 있다. 실제 모델은 길이가 길수록 일부 지시를 놓칠 수 있다.

특히 충돌 가능성이 있는 지점:

- “전문용어 표면 금지”와 “전문가 근거 보기에는 전문 근거 보존”
- “기본 리딩은 JudgmentPack만 사용”과 “기본도 정보량을 줄이지 않는다”
- “구체적으로 쓰라”와 “근거 없는 구체 사건을 지어내지 말라”
- “상담가처럼 말하라”와 “물리적 대면 묘사 금지”

정적으론 지시가 존재하지만, 실제 출력에서 어느 지시가 우선되는지는 별도 검증 필요.

### R3. 기본 리딩과 AI 기본 리딩의 경계가 혼동될 수 있다

`basicReadingRenderer.ts`는 AI 없는 즉시 기본 리딩이고, `DEFAULT_STANDARD_INSTRUCTION`은 AI 기본 리딩 지시다. 둘 다 “기본 리딩”이라는 이름을 공유한다.

Claude Code가 이후 작업할 때 다음을 구분해야 한다.

- `buildBasicReading()` = 브라우저/룰 기반 즉시 카드
- `DEFAULT_STANDARD_INSTRUCTION` = AI가 생성하는 기본 종합 리딩
- `JudgmentPack Evidence Gate` = AI 기본 리딩의 근거 제한 장치

이 구분을 문서/주석/UI 용어에서 명확히 하지 않으면 작업자가 혼동할 수 있다.

### R4. 토픽 심화는 정적으론 안전하지만 “유료감”은 미검증이다

토픽 심화는 domain 한정, 새 판단 금지, 5섹션 구조가 잘 잡혀 있다. 하지만 1000~2500자 소형 리포트가 실제로 돈 낼 만한지, 사용자가 “짧지만 정확하다”고 느낄지는 생성문이 필요하다.

### R5. 타로 조합은 참고용이지만 실제 출력에서 과장될 수 있다

`tarotCombos.ts`는 참고용/단정 금지를 명시한다. 그러나 실제 LLM이 “탑 + 소드10” 같은 강한 조합을 공포스럽게 풀 가능성은 남아 있다. 실제 생성문에서 강한 카드 조합 5~10개를 별도 검수해야 한다.

## 실제 리딩 없이 지금 할 수 있는 검수 체크리스트

Claude Code가 API 키 없이 이어서 할 수 있는 작업이다.

### A. 프롬프트 렌더링 스냅샷 확대

현재 `reading.test.ts`는 S-5 일부 케이스를 확인한다. 다음 케이스를 추가하면 실제 생성문 없이도 품질 레일을 더 잠글 수 있다.

| 케이스 | 확인할 것 |
|---|---|
| 재다신약 또는 돈 위험 케이스 | `MONEY_RISK_MEDIUM`, 투자/수익 단정 금지, 고정비/대여/동업 점검 actionFrame |
| 관인상생 또는 구조 solid 케이스 | `STRUCTURE_SOLID_SUPPORT`, 강점 활용, 과확장 금지 |
| 조후 미충족 케이스 | `CLIMATE_BALANCE_NEEDED`, 건강 진단 금지, 생활 리듬 보완 |
| 십성 편중 케이스 | `TENGOD_SKEW_TRAIT`, 빈 축을 결함으로 말하지 말라는 금지 |
| 상문/조객 발동 케이스 | 초상/죽음/불행 금지 gloss 동반 여부 |
| 대운 충 강한 케이스 | “자리·환경이 바뀌기 쉬운 구간”으로 완화되는지 |
| 타로 강한 충격 조합 | “붕괴/상처”가 공포 예언이 아니라 정리/전환으로 완화되는지 |
| 순수 타로 고급 | 사주 섹션을 만들지 말라는 지시가 들어가는지 |
| 통합 리딩 | 사주/타로 둘 다 사용하라는 고정 구조가 들어가는지 |
| topicDeep love/money/career/health/year | 해당 domain만 쓰고 다른 domain 섞지 말라는 지시가 들어가는지 |

### B. 금지어 정적 검사 추가

실제 생성문은 없지만, 프롬프트/폴백/룰 결론에 금지어가 섞이는지는 정적 검사 가능하다.

검사 대상:

- `src/prompts/systemPrompt.ts`
- `src/lib/judgmentEngine.ts`
- fallback 계열 파일
- basic renderer 출력 포맷 계열 파일

금지어 후보:

- 반드시 죽음
- 무조건 이혼
- 병에 걸립니다
- 투자하세요
- 큰돈을 벌게 됩니다
- 지금 퇴사하세요
- 당장 창업하세요
- 가족 때문에 망합니다

주의: 시스템 프롬프트 안의 “금지 예시”로 등장하는 단어는 예외 처리해야 한다.

### C. “기본 리딩” 용어 정리

문서나 코드 주석에서 다음 용어를 분리하는 것이 좋다.

| 현재 표현 | 권장 표현 |
|---|---|
| 기본 리딩 | 즉시 기본 카드 / AI 기본 리포트 중 하나로 구분 |
| P0 룰 렌더러 | 즉시 기본 카드 |
| DEFAULT_STANDARD_INSTRUCTION | AI 기본 종합 리포트 지시 |
| topicDeep | AI 토픽 심화 리포트 |

### D. 타로 강한 카드 안전 검수 추가

타로는 실제 생성 전에도 강한 조합 프롬프트에 안전 완충이 들어가는지 확인할 수 있다.

우선 테스트할 조합:

- 죽음 + 탑
- 탑 + 소드 10
- 탑 + 소드 3
- 악마 + 탑
- 소드 3 + 소드 9
- 소드 8 + 소드 9
- 펜타클 5 + 컵 5

기대 기준:

- 죽음/파산/이별/사고를 확정하지 않는다.
- “강한 전환”, “정리”, “상처를 인정하고 회복” 같은 완충 표현이 들어간다.
- 행동 조언으로 닫힌다.

## 실제 생성문 검수 전까지의 임시 합격 기준

실제 리딩을 못 보는 동안에는 아래 기준을 모두 만족하면 “정적 합격”으로 둔다.

| 기준 | 합격 조건 |
|---|---|
| 근거 주입 | 리딩 타입별로 필요한 근거 블록이 프롬프트에 존재 |
| 근거 제한 | 기본은 JudgmentPack, 고급은 Anchor+Raw 구조 유지 |
| 안전 지시 | 전역/도메인/운한/타로 안전 지시 존재 |
| 구체성 재료 | 생활 처방, actionFrame, tarot scene/advice 등 구체 행동 재료 존재 |
| 용어 관리 | 본문 용어 금지, 전문가 근거 보존 지시 존재 |
| 불확실성 | confidence, counterEvidence, uncertainty를 말투에 반영하라는 지시 존재 |
| 테스트 고정 | 위 조건 중 핵심은 `reading.test.ts` 등 자동 테스트로 고정 |

## 실제 생성문을 볼 수 있게 되면 반드시 할 검수

API 키 있는 환경에서 다음 순서로 확인한다.

1. 기본 사주 리딩 5개
2. 고급 사주 리딩 5개
3. topicDeep 5종 각 2개씩
4. 순수 타로 5개
5. 통합 리딩 3개
6. 상대 완전분석 3개
7. 후속 질문 5개

각 출력은 `docs/validation/reading-quality-validation.md` 표로 평가한다.

특히 사람이 직접 봐야 할 항목:

- “내 얘기 같다” 체감
- 문장 중복
- 전문용어 노출
- 불안 조장
- 조언의 실행 가능성
- 유료감
- 마지막 섹션까지 완결 여부

## Claude Code 다음 작업 지시

아래 작업을 우선순위대로 진행하면 된다.
